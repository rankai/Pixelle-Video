## 1. 用户目标

应用工作台采用“左侧轻量输入、右侧生成结果”的结构。右侧不是技术交付清单，也不是只显示一行摘要的传统历史表格，而应让门店老板完成三件事：

1. 立即看到本次生成的完整结果；
2. 在同一页面比较、复制、编辑或采用不同候选；
3. 向下滚动即可找回同一项目以前的完整生成结果。

用户确认的核心模型是：

```text
一次点击生成
→ 一个生成批次
→ 一条历史记录
→ 一块完整结果
→ 块内直接展示本次全部输出
```

例如，爆款标题一次生成 6 个候选：

```text
不是 6 条历史记录
也不是 1 行摘要 + 点击详情才看 6 条

而是：
1 个时间分组记录块
└── 直接展示 6 个标题候选
```

## 2. 核心产品决策

### 2.1 一次生成等于一个历史记录块

历史记录聚合边界为一个 `AppRun`：

- 用户再次点击生成：新增一个记录块；
- 同一 AppRun 的排队、运行、失败重试和恢复：仍属于原记录块；
- 复制、编辑、下载、预览和交给发布中心：不新增记录块；
- 从一个应用交给另一个应用并在目标应用真正执行生成：目标应用新增自己的记录块。

记录块头部只显示用户理解的信息：

- 生成时间；
- 业务状态；
- 必要时显示来源应用；
- 本次结果数量或成品类型。

不得在正常界面显示：

- AppRun ID、Artifact ID、ArtifactVersion ID；
- Provider、模型、workflow、session；
- ContextSnapshot、文件路径或结构化 JSON；
- 重试栈、诊断日志和内部步骤。

### 2.2 记录块内直接展示完整输出

主界面不采用“历史列表摘要 → 查看详情 → 才看到结果”的强制路径。

每个记录块直接展示该次生成的全部业务结果：

- 标题：全部标题候选；
- 文案：全部文案方案；
- 图文：一个完整图文成品卡；
- 数字人：一个最终视频成品卡。

详情或预览只承担以下职责：

- 放大查看媒体；
- 播放视频；
- 查看图文全部页面；
- 进入编辑；
- 查看次级交付信息。

详情不得成为查看标题或文案候选的必经步骤。

### 2.3 多候选与单成品必须区分

四个应用的输出基数不同，不能用一套“多个候选卡片”强行统一。

| 应用 | 一次生成的用户结果 | 记录块展示 |
| --- | --- | --- |
| 门店营销文案 | 多个文案方案 | 块内逐条完整展示 |
| 爆款标题 | 多个标题候选，目标默认 6 条 | 块内逐条完整展示 |
| 抖音图文 | 1 个完整图文成品，内部含多页 | 块内只显示 1 个图文成品卡 |
| 数字人口播 | 1 个最终视频成品 | 块内只显示 1 个视频成品卡 |

禁止为了视觉热闹而：

- 把图文内部每一页伪装成多个独立成品；
- 把数字人的视频、封面、口播稿和发布文案伪装成多个候选；
- 为图文或数字人生成没有业务价值的多个成品备选；
- 复制参考产品“一次生成很多视频”的产品模型。

### 2.4 默认先看当前应用，保留项目全局视图

每个应用右侧默认显示：

```text
当前项目 + 当前应用的生成记录
```

这样门店老板在爆款标题页面看到的首先都是标题记录，在数字人页面看到的首先都是视频记录，不会混入不同形态的结果。

工具栏仅保留一个轻量筛选：

```text
当前应用 / 全部成果
```

选择“全部成果”时，才按时间混排当前项目四个应用的记录，并显示“来源应用”标签。

该切换应记住当前会话选择，但不做复杂的筛选管理器。

### 2.5 最新记录在最上方

- 按 `result_available_at DESC` 排序；
- 新生成完成后在顶部插入新的完整记录块；
- 历史块不因复制、预览或下载改变时间；
- 生成中的块可先出现在顶部，完成后原地更新；
- 不再单独增加“本次结果 / 历史记录”两套页面。

本次结果就是历史流最上方的第一个记录块。

## 3. 参考页面结论

用户提供的万相营造截图确认了三种模式。

### 3.1 爆款标题

一次生成对应一个带时间的历史记录块，块内使用网格直接展示 6 个标题。每个标题可独立复制、编辑或生成相似内容。

Pixelle 借鉴：

- 生成批次按时间分组；
- 候选在同一记录块内完整展示；
- 候选操作就近放置；
- 向下滚动连续查看旧记录。

Pixelle 不照搬：

- 过小字号和低对比度；
- 每个候选堆放过多操作；
- 超宽屏固定三列；
- 对非电商门店无意义的评价与购买入口。

### 3.2 门店营销文案

一次生成的多个长文案都位于同一个时间记录块，文案正文直接可读，不需要先打开详情。

Pixelle 应保持：

- 一条文案方案一个轻量内容项；
- 正文直接展示；
- 复制和编辑就近；
- 风格标签作为弱信息，不与正文争夺层级。

### 3.3 视频结果

参考产品一次可以生成多个视频，因此一个记录块展示多个视频卡。

Pixelle 的业务不同：

- 抖音图文一次只交付一个完整图文成品；
- 数字人口播一次只交付一个最终视频；
- 所以每个记录块只展示一个成品卡；
- 点击成品卡直接查看真实预览。

这里借鉴的是“历史记录块内展示真实结果”，不是“必须一次生成很多媒体结果”。

## 4. 页面信息架构

### 4.1 右侧面板

统一标题：

```text
生成记录                         [当前应用⌄]
```

记录流示例：

```text
今天 18:20:07                                    已完成
本次生成 6 个标题

[标题 1]  [标题 2]
[标题 3]  [标题 4]
[标题 5]  [标题 6]

今天 17:42:31                                    已完成
本次生成 6 个标题

[标题 1]  [标题 2]
[标题 3]  [标题 4]
[标题 5]  [标题 6]
```

记录块之间使用留白和浅层卡片区分，不增加重边框、双层描边和大面积渐变。

### 4.2 记录块头部

默认显示：

1. 生成时间；
2. 状态；
3. 结果数量或成品类型；
4. “全部成果”模式下的来源应用。

可选次级菜单：

- 删除记录仅在产品明确支持可恢复删除后出现；
- 重新生成；
- 查看生成输入。

不得默认显示“查看详情”作为唯一入口，因为结果已经在块内。

### 4.3 标题候选项

标题记录块目标默认展示 6 条实际生成结果；如果以后候选数量可配置，则展示该 AppRun 的全部实际候选，不在前端硬编码截断。

每条候选显示：

- 标题正文；
- 风格弱标签；
- 复制；
- 编辑；
- 采用。

“生成相似”属于次级动作，可放入更多菜单，避免每个候选出现四五个按钮。

标题候选不需要“查看详情”。

### 4.4 文案方案项

每条文案方案显示：

- 风格或用途弱标签；
- 完整文案正文；
- 复制；
- 编辑；
- 采用。

正文较长时：

- 记录块仍包含完整内容；
- 允许单条内容视觉折叠到合理高度；
- 折叠控件写“展开全文”，而不是“查看详情”；
- 复制始终复制完整正文；
- 展开只影响展示，不改变 ArtifactVersion。

### 4.5 抖音图文成品卡

一次生成记录只显示一个图文成品卡：

```text
[封面真实缩略图]  三公里上班族下午茶
                    3 页
                    [预览] [去发布]
```

默认可见信息严格限制为：

1. 一张真实封面缩略图；
2. 一个用户可理解的标题；
3. 页数；
4. 最多两个轻量操作：`预览`、`去发布`。

交互：

- 点击卡片或“预览”，打开真实图文预览；
- 预览按顺序展示全部实际页面；
- 不使用“第 1 页 / 第 2 页 / 第 3 页”Tab 作为主要浏览方式；
- 不在记录块罗列分页计划、Artifact、版本和渲染步骤；
- 修改单页属于预览内次级操作。
- 下载图片、下载全部、复制发布文案和编辑放在预览层，不挤在成品卡上；
- 卡片右上角仅在确有次级操作时显示一个 `更多` 菜单；
- “已生成发布文案”“已完成渲染”等成功状态不重复显示，成功由可预览成品本身表达；
- 失败时才用一行错误说明和一个“重试”操作替换正常卡片动作。

成品卡不得显示：

- 分页计划和各页摘要；
- 文案版本、图片版本和结果版本；
- 生成参数、模板名、模型、Provider；
- 文件名、路径、大小和格式；
- “下载图片组 / 下载 ZIP / 复制发布文案 / 保存版本 / 重新渲染”等按钮群；
- 与用户下一步无关的状态标签。

### 4.6 数字人口播成品卡

一次生成记录只显示一个最终视频卡：

```text
[最终封面或视频首帧]  门店下午茶推荐口播
                        00:28
                        [播放] [去发布]
```

默认可见信息严格限制为：

1. 一个真实视频首帧或最终封面；
2. 一个用户可理解的标题；
3. 视频时长；
4. 最多两个轻量操作：`播放`、`去发布`。

交互：

- 点击卡片或“播放”，直接打开最终合成视频；
- 预览首屏必须是真实 `<video>`，不是交付文件清单；
- 封面、发布标题、描述和话题作为播放器下方的次级信息；
- 口播稿、声音绑定和生成步骤默认隐藏；
- 失败时才显示重试和诊断入口。
- 下载视频、下载封面、复制发布文案和编辑放在播放器预览层；
- 图片模式/视频模式、声音名称、字幕状态不在正常卡片重复展示；
- 卡片右上角仅在确有次级操作时显示一个 `更多` 菜单；
- “已生成视频”“待确认”“Artifact 完整”等技术或流程状态不占用成品卡正文区域。

成品卡不得显示：

- 视频、封面、发布文案、口播稿四条交付清单；
- 数字人模式、VoiceProfile、声音绑定详情；
- TTS、RunningHub、后期合成步骤；
- Provider、任务 ID、版本号、重试次数；
- 下载、复制、交付、编辑、重渲染同时平铺形成按钮群；
- 正常成功场景不需要用户处理的提示。

最终发布按钮仍不自动点击。

## 5. 响应式和视觉规则

### 5.1 布局

桌面端：

- 左侧创作区保持固定合理宽度；
- 右侧记录区使用剩余空间；
- 页面两侧不保留大面积无效空白；
- 不照搬参考产品的超宽三列。

标题候选：

- 右侧有效宽度 ≥ 1100px：2 列；
- 700px–1099px：2 列但收紧间距；
- < 700px：1 列。

长文案：

- 始终 1 列，保证阅读宽度；
- 单行文本最大阅读宽度控制在约 70–90 个中文字符；
- 不把长文案压成三列卡片。

图文和数字人：

- 每个历史记录块始终只有 1 个主成品卡；
- 宽屏采用“缩略图 + 信息”横向布局；
- 窄屏改为纵向。
- 成品卡内部只有一个视觉焦点：真实封面或视频首帧；
- 标题最多两行，超出后截断，完整标题在预览中显示；
- 元信息只保留页数或时长，不堆叠 Tag；
- 卡片常驻按钮最多两个；
- 整张卡片可点击，不能要求用户精确点击小字链接。

### 5.2 媒体成品卡显示预算

图文和数字人成品卡采用统一“显示预算”：

| 层级 | 图文 | 数字人 |
| --- | --- | --- |
| 必须显示 | 真实封面、标题 | 真实首帧/封面、标题 |
| 可显示 | 页数 | 时长 |
| 常驻操作 | 预览、去发布 | 播放、去发布 |
| 预览层操作 | 下载、复制文案、编辑 | 下载视频、复制文案、查看封面 |
| 更多菜单 | 重新生成等低频操作 | 重新生成等低频操作 |
| 默认隐藏 | 页面计划、版本、文件、模型、模板 | 模式、声音绑定、字幕、步骤、版本 |

任何新增字段或按钮进入成品卡前，必须回答：

```text
门店老板是否需要在“决定要不要打开这个成品”之前看到它？
```

如果答案是否定的，则放入预览层、更多菜单或完全不展示。

### 5.3 Pixelle 主题一致性

必须复用现有：

- 页面容器；
- 字号层级；
- 间距、圆角、边框和阴影 tokens；
- Button、Tag、Select、Modal、Drawer；
- 禁用态与焦点态。

不得直接复制参考产品的：

- 灰底输入块；
- 蓝色风格角标造型；
- 按钮尺寸；
- 卡片阴影；
- 字体和低对比度文本。

### 5.4 可访问性

截图只能确认视觉组织，不能证明完整无障碍能力。实施必须验证：

- 正文和次级文字对比度；
- 所有候选操作可键盘访问；
- 操作目标不小于 36px，优先 40px；
- 生成完成通过可感知状态提示，不仅依靠颜色；
- Modal/Drawer 打开后焦点进入，关闭后返回原触发项；
- 视频有键盘播放控制；
- 200% 缩放不遮挡生成按钮和结果操作；
- 窄屏结果项不横向溢出。

## 6. 领域模型

### 6.1 聚合边界

```text
GenerationRecordBlock
= 一个 AppRun
+ 该 AppRun 产出的业务结果项
+ 固定的 ArtifactVersion
```

`GenerationRecordBlock` 是只读投影，不新建第二套事实表。

现有事实源：

- `app_runs`：一次生成任务；
- `artifacts.source_app_run_id`：产物归属；
- `artifact_versions.source_app_run_id`：版本归属；
- `artifact_handoffs`：跨应用固定交接；
- `app_events`：选择、复制、编辑和交付事件；
- 数字人 binding/session：恢复与最终媒体定位。

### 6.2 结果形态

```text
multi_copy
multi_title
single_carousel
single_video
```

数据模型必须表达输出基数，前端不得凭文件数量猜测：

```json
{
  "record_id": "app_run_id",
  "project_id": "project-...",
  "app_id": "builtin.viral-titles",
  "result_shape": "multi_title",
  "items": [
    {
      "item_id": "candidate-1",
      "kind": "title",
      "text": "标题候选",
      "actions": ["copy", "select"]
    }
  ]
}
```

图文即使有 5 个页面文件，仍然是：

```json
{
  "result_shape": "single_carousel",
  "items": [
    {
      "item_id": "carousel-1",
      "kind": "carousel",
      "page_count": 5,
      "details_available": ["pages", "publish_copy"]
    }
  ]
}
```

数字人即使同时生成视频、封面、口播稿和发布文案，仍然是：

```json
{
  "result_shape": "single_video",
  "items": [
    {
      "item_id": "video-1",
      "kind": "video",
      "details_available": ["cover", "publish_copy", "spoken_script", "download"]
    }
  ]
}
```

### 6.3 记录块读模型

建议 DTO：

```json
{
  "schema_version": 1,
  "record_id": "app-run-id",
  "app_run_id": "app-run-id",
  "project_id": "project-id",
  "app_id": "builtin.viral-titles",
  "app_name": "爆款标题",
  "result_shape": "multi_title",
  "status": "completed",
  "created_at": "2026-07-30T10:20:00Z",
  "result_available_at": "2026-07-30T10:20:08Z",
  "summary": "工作日下午茶标题",
  "compatibility": {
    "state": "normal"
  },
  "items": [
    {
      "item_id": "candidate-1",
      "kind": "title",
      "text": "工作日下午茶不用愁，现磨咖啡配面包",
      "label": "痛点标题",
      "actions": ["copy", "select"]
    }
  ]
}
```

媒体结果项只返回受控缩略图、预览和下载引用，禁止返回绝对路径。

### 6.4 版本语义

- `original_version`：AppRun 首次生成的版本；
- `display_version`：用户最后保存的有效版本；
- `handoff_version`：跨应用或发布时固定使用的版本。

记录块默认展示 `display_version`。

编辑某个标题或文案：

- 创建新的 ArtifactVersion；
- 原记录块原地更新该结果项；
- 不新增历史记录块；
- 记录块可在次级信息显示“已编辑”；
- 已交付版本继续固定，不被后续编辑静默替换。

### 6.5 历史兼容

旧数据兼容顺序：

1. 使用 `source_app_run_id` 精确聚合；
2. 使用 `AppRun.output_artifact_ids` 与 artifact ownership；
3. 仍无法确定时标记 `compatibility.state=legacy_unavailable`，并在该记录内返回普通用户可理解的 `unavailable_reason`；
4. 可安全解析的旧结果继续完整展示；
5. 无法安全聚合的记录显示时间、来源、状态和“历史结果暂不可预览”；
6. 读取旧数据不得补写或修改历史 Artifact。

## 7. API 方案

### 7.1 记录块列表

```text
GET /api/content-projects/{project_id}/result-records
```

参数：

- `cursor`
- `limit`：默认 10 个记录块，最大 20
- `scope=current_app|all_results`
- `app_id`
- `result_shape`
- `status`

响应：

```json
{
  "schema_version": 1,
  "project_id": "project-id",
  "scope": "current_app",
  "app_id": "builtin.viral-titles",
  "records": [],
  "next_cursor": null
}
```

排序：

```text
result_available_at DESC
app_run_id DESC
```

文本结果：

- 列表响应直接返回完整候选文本；
- 不要求再请求详情才能阅读；
- 生成领域可以在创建 AppRun 前限制用户请求的候选目标数；
- AppRun 已实际产出的候选必须全部投影返回，不得截断或静默丢失。

媒体结果：

- 列表返回一个成品项及缩略图/首帧；
- 图文不返回全部原图二进制；
- 视频不在列表自动加载完整文件。

### 7.2 媒体预览

继续使用受控 Artifact 预览/下载接口，并新增或统一：

```text
GET /api/result-records/{record_id}/preview
```

按结果形态返回：

- 图文：页面顺序、受控图片引用、发布文案；
- 数字人：最终视频引用、封面、时长、发布标题、描述和话题。

打开预览不得：

- 新建 AppRun；
- 触发渲染；
- 调用 Provider；
- 修改固定版本；
- 自动交给发布中心。

### 7.3 写操作

不创建万能更新接口，继续复用领域服务：

- 复制：前端剪贴板 + app event；
- 采用标题/文案：selected state/ArtifactVersion；
- 编辑：append ArtifactVersion；
- 重新生成：创建新 AppRun、新记录块；
- 图文下载：现有 Artifact 下载；
- 数字人下载：现有受控媒体下载；
- 发布交接：PublishPackage V2。

## 8. 前端组件

建议共享结构：

```text
ProjectGenerationHistory
├── GenerationHistoryToolbar
├── GenerationRecordBlock
│   ├── GenerationRecordHeader
│   ├── MultiCopyResults
│   ├── MultiTitleResults
│   ├── SingleCarouselResultCard
│   └── SingleVideoResultCard
├── CarouselPreviewModal
├── VideoPreviewModal
└── ResultEditDrawer
```

四个应用只传：

- 当前项目 ID；
- 当前应用 ID；
- 结果形态；
- 编辑回调；
- 跨应用回调；
- 发布中心回调；
- Feature flag。

不得复制四套：

- 历史查询；
- cursor 分页；
- 时间分组；
- 加载/错误状态；
- Modal 焦点管理；
- 事件记录。

### 8.1 加载策略

- 首屏加载最新 10 个记录块；
- 文本候选随记录块返回；
- 媒体只加载缩略图；
- 真实图文页和视频在用户点击预览后加载；
- 图片使用 lazy loading；
- 关闭预览释放 Blob URL；
- 当前会话缓存已打开的媒体预览；
- 新生成或编辑后只失效当前项目、当前 AppRun；
- 禁止前端按候选逐条请求 Artifact，避免 N+1。

### 8.2 状态

空态：

```text
还没有生成记录
完成左侧设置并点击生成，结果会保存在这里。
```

生成中：

- 顶部出现一个当前记录块；
- 块内显示清晰进度，不展示假结果骨架；
- 完成后原地替换为完整结果。

加载失败：

- 左侧输入保持可用；
- 右侧显示“生成记录暂时无法读取”；
- 重试仅重试查询，不创建 AppRun。

媒体失败：

- 保留标题、文案、时间和下载；
- 显示“预览暂不可用，仍可下载”；
- 不循环请求或重新触发 Provider。

## 9. 数据库与性能

优先复用现有表，不新增 `result_records` 持久化表。

按需增加索引：

```sql
CREATE INDEX IF NOT EXISTS idx_app_runs_project_app_updated
ON app_runs(project_id, app_id, updated_at DESC, app_run_id DESC);

CREATE INDEX IF NOT EXISTS idx_artifacts_source_run
ON artifacts(source_app_run_id);

CREATE INDEX IF NOT EXISTS idx_artifact_versions_source_run_created
ON artifact_versions(source_app_run_id, created_at DESC, artifact_version_id DESC);
```

性能预算：

- 本地最新 10 个记录块 API：P95 ≤ 350ms；
- 文本记录首屏可直接阅读；
- 列表不下载原图或完整视频；
- 媒体预览点击后 1 秒内出现可见加载状态；
- cursor 翻页稳定，无重复、遗漏；
- 单项目大量历史记录时不一次性渲染全部媒体。

## 10. Feature Flag 与回滚

建议同步开关：

```text
VITE_APP_RESULT_HISTORY_V1
PIXELLE_APP_RESULT_HISTORY_V1
```

开启：

- 四应用右侧使用完整记录块；
- 后端开放记录块投影和媒体预览。

关闭：

- 回到当前结果区；
- 不删除 AppRun、Artifact、ArtifactVersion、Handoff 或事件；
- 不改变项目或品牌快照；
- 不影响数字人声音绑定；
- 不改变发布人工确认边界。

桌面前端和 FastAPI sidecar 必须同步解析开关。

## 11. 分阶段实施

### APP-RESULT-HISTORY-0：契约与视觉基线

目标：

- 登记 `CR-APP-RESULT-HISTORY-001`；
- 协调层切换 `current_stage=APP-RESULT-HISTORY-0`；
- 冻结“一次 AppRun 一个记录块”；
- 冻结四种 `result_shape`；
- 冻结标题默认 6 候选及“展示全部实际候选”原则；
- 保存四应用当前视觉基线；
- 不改业务 UI 和数据库。

Gate `PG-ARH-A`：

- 6 个标题=1 个记录块+6 个结果项；
- 3 个文案=1 个记录块+3 个结果项；
- 5 页图文=1 个记录块+1 个图文成品项；
- video+cover+copy=1 个记录块+1 个视频成品项；
- 独立六维 Entry 审查 P0/P1=0。

### APP-RESULT-HISTORY-1：后端只读投影

目标：

- 实现记录块列表；
- 实现稳定 cursor；
- 实现完整文本候选投影；
- 实现单图文、单视频聚合；
- 实现 legacy/null/digital-human 兼容；
- 按需增加索引。

Gate `PG-ARH-B`：

- 项目隔离和当前应用过滤正确；
- 一次生成不拆成多条历史记录；
- 图文页面不拆成多个成品；
- 数字人附件不拆成多个成品；
- 列表不存在 N+1；
- 旧数据读取零写；
- 独立六维审查 P0/P1=0。

### APP-RESULT-HISTORY-2：文本记录块

目标：

- 接入共享记录流；
- 实现标题和文案完整记录块；
- 完成复制、采用和编辑；
- 实现当前应用/全部成果切换；
- 完成响应式布局。

Gate `PG-ARH-C`：

- 标题一次生成的全部候选直接可见；
- 文案无需打开 Modal 即可阅读；
- 复制、编辑、采用操作语义正确；
- 再次生成在顶部新增第二个记录块；
- 1440/1280/900/390 四视口通过；
- 键盘顺序、焦点态和 200% 缩放通过；
- 独立六维审查 P0/P1=0。

### APP-RESULT-HISTORY-3：单成品媒体记录块

目标：

- 图文记录块只显示一个真实成品卡；
- 点击图文卡直接预览全部页面；
- 数字人记录块只显示一个最终视频卡；
- 点击视频卡直接播放最终成片；
- 媒体失败保留下载和文本回退。

Gate `PG-ARH-D`：

- 3/5/8 页图文均只有一个成品卡；
- 预览展示全部实际页面且无分页 Tab 主交互；
- 数字人只有一个视频成品卡；
- 图文卡常驻信息仅为封面、标题、页数和最多两个操作；
- 视频卡常驻信息仅为首帧/封面、标题、时长和最多两个操作；
- 下载、复制、编辑和技术信息不在卡片上形成按钮群；
- 播放器、封面、发布文案版本一致；
- 重启后旧媒体记录仍可查看；
- 预览不触发 Provider；
- Blob URL 释放且重复打开无泄漏；
- 最终发布按钮点击=0；
- 独立六维审查 P0/P1=0。

- 四应用记录块语义一致；

## 13. 验收标准

必须全部满足：

1. 一次生成只产生一个历史记录块；
2. 记录块内直接展示本次完整业务输出；
3. 标题一次生成的全部候选直接可比较和操作；
4. 文案方案无需进入详情即可阅读；
5. 图文一次生成只显示一个完整图文成品卡；
6. 数字人一次生成只显示一个最终视频成品卡；
7. 图文卡默认只显示封面、标题、页数以及预览和去发布；
8. 数字人卡默认只显示首帧/封面、标题、时长以及播放和去发布；
9. 两类媒体成品卡的常驻操作均不超过两个；
10. 下载、复制、编辑、版本和技术信息不会挤在成品卡上；
11. 点击图文卡直接预览全部实际页面；
12. 点击视频卡直接播放最终成片；

14. 重试、编辑、复制和下载不伪造新记录；
15. 用户能向下滚动找回当前项目以前的完整结果；
16. 默认当前应用记录，按需切换全部成果；
17. 页面不显示技术清单和内部字段；
18. 复用 Pixelle tokens 和共享组件；
19. 历史记录重启后仍可读；
20. Feature flag 可回滚且不删除数据；
21. 最终发布仍由用户人工确认。

## 14. 明确不做

- 不把一个候选拆成一条 AppRun；
- 不把图文每页拆成独立成品；
- 不把数字人视频、封面、文案和脚本拆成多个成品；
- 不为图文和数字人增加没有业务价值的批量候选生成；
- 不把下载、复制、编辑、交付、重渲染等操作全部平铺在媒体成品卡；
- 不在正常媒体卡重复展示“已完成”“已生成”“待确认”等无行动价值的信息；
- 不新建第二套结果事实数据库；
- 不在记录块展示模型、Provider、技术版本或文件路径；
- 不把“我的项目”变成资产类型；
- 不改账户、租户、RBAC、套餐或支付；
- 不自动点击任何平台最终发布按钮；
- 不在本文确认前切换协调台账 `current_stage`。
