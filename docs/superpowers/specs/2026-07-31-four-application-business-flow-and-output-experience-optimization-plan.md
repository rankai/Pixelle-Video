## 1. 评审结论

原方案“一个应用只解决一个问题、左侧少量输入、右侧直接看结果、分别优化业务链路”的方向正确，可以继续执行。

本次评审对实施方式作出以下收口：

1. 不建设内容评分、候选差异度、事实覆盖率、版式占用率或口型精度等自动质量合同；
2. 不因内容“不够好”自动换模型、自动重试、自动降级或同时运行多套策略；
3. 只保留字段、类型、数量、文件引用、权限、已确认合规规则和平台硬限制等客观边界校验；结构错误最多进行一次有界 repair；
4. 风格样例复用现有代码随包发布的 Style Preset，不建设数据库、管理后台或第二套风格目录；
5. 图文只做当前任务需要的图片描述、推荐和三类可靠版式，不建设素材评分平台、向量检索或通用自动布局引擎；
6. 数字人复用已经完成的轻应用、图片/视频自动识别和声音绑定，不重新开发双模式与 VoiceProfile；
7. 结果区复用现有生成历史和 Artifact 投影，不新建结果记录、结果版本或第二份产物权威；
8. 不新增第三套应用运行路径或新的 rollout flag；默认在当前权威路径上修改。只有真实历史 Artifact 需要保持不可变读取时，才允许对客观输出结构做一次明确版本演进，但旧版本不再继续写入；
9. 不把“先做纯页面、以后再接业务”作为可合入阶段，每个应用按真实纵向闭环完成；
10. Windows 安装验收继续属于上位 Program，不作为本方案业务体验优化的完成条件。

`APP-RESULT-HISTORY-output-quality-review-2026-07-30.md` 中记录的真实内容问题继续作为问题证据；其中“增加质量规则、占用率检查”等机制建议不作为本方案要求，以本文件和 `docs/development-principles.md` 为准。

文案和标题应用的固定业务模型是：

```text
项目资料
+ 用户选择
+ 用户本次输入
+ 当前应用的 Prompt 与风格样例
→ 一次提交给现有大模型
→ 解析必要的客观结果结构
→ 直接交给用户选择、复制或编辑
```

应用代码不在模型返回后重新判断“角度是否一致、差异是否足够、表达是否高级、是否像爆款”，也不根据这些主观判断拒绝整批结果或再次调用模型。内容效果由输入资料、用户选择、Prompt、风格样例和当前模型共同决定。

## 2. 当前问题、影响与根因

### 2.1 当前问题

- 页面已经完成第一轮轻量化，但文本应用仍有项目和内部结果结构残留；
- 营销文案和标题可以生成，但内容泛化、候选重复，不能稳定体现本次项目；
- 抖音图文已有历史记录和完整预览，但旧样片存在图文不匹配、标题过大和空白明显；
- 数字人轻应用主路径已经完成，但真实成片仍需改善口播稿、字幕和已观察到的媒体效果；
- 当前文本执行器仍存在把主观内容问题当成输出合同处理的代码，例如角度一致、标题重复、泛化禁用词和风险标签导致整批失败或 repair。

### 2.2 用户影响

目标用户需要理解内部版本、风险标签和结构字段，或者在生成后仍要花较多时间筛选、重写和排版，削弱“选择少量信息即可得到可用结果”的产品价值。

### 2.3 根因

根因分别位于四个应用自己的业务链路：

| 应用 | 根因 |
| --- | --- |
| 门店营销文案 | 项目事实没有以适合文案创作的方式进入 Prompt；三条候选的写作任务不清楚 |
| 爆款标题 | 内容来源表达过重；Prompt、样例和当前模型没有稳定产出自然且不同的标题 |
| 抖音图文 | 图片描述、分页文案、页面角色和最终版式没有形成直接对应 |
| 数字人口播 | 普通文案未整理为口播稿；已观察到的字幕和媒体效果需要在现有工作流内调整 |

结果历史、项目、品牌包、模型管理、VoiceProfile 和发布中心不是本次问题根因，不重新建设。

### 2.4 最小充分方案

在现有应用中心、项目上下文、Style Preset、LLM Port、图文 Renderer、数字人链路和结果历史上，分别完成：

```text
少量业务输入
→ 应用自己的 Prompt / 素材处理 / 媒体处理
→ 现有 AppRun 与 Artifact
→ 一块可直接理解的历史记录
→ 复制、编辑、预览、下载或交给发布中心
```

## 3. 明确不做

本 Change Request 不做：

- 通用内容质量平台、自动评分、自动筛选或自动合格判定；
- 多模型竞赛、模型 fallback chain、后台质量重试；
- 风格管理后台、数据库风格表或租户级风格配置；
- 通用素材理解平台、向量库、素材分数和自动版式引擎；
- 新项目系统、新品牌包、新资产库或新的结果历史；
- 新的 AppRunner、Artifact、PublishPackage 或任务状态权威；
- 为每个应用机械创建 Interface、Port、Adapter、Planner 或空目录；
- 为草稿合同或无调用者测试创建的新 Schema 版本、第三套 UI 路径或没有删除条件的新 feature flag；
- 为未发布草稿合同、旧测试或无调用者代码增加兼容层；
- 自动点击任何平台最终发布按钮；
- Windows 安装、平台 WebView SLA 和真实平台 rollback 验收。

## 4. 四个应用的共同体验

### 4.1 页面结构

桌面宽度使用左右工作台：

- 左侧：当前任务所需输入；
- 右侧：当前结果和历史记录；
- 页面使用应用中心现有容器、字体、间距、按钮、Tag、Modal 和状态 Token；
- 宽屏充分使用空间，不形成过大的两侧留白；
- 窄屏按输入在前、结果在后的顺序自然重排。

不新增一套 App Workbench 设计系统。复用现有 `AppWorkbenchShell`、项目选择器、Style Picker、资产选择器和结果历史；只有职责已经不同的应用面板才在各自 feature 内拆分。

### 4.2 项目选择

四个应用都使用同一个轻量项目入口：

```text
当前项目：工作日下午茶套餐
主推：现磨咖啡 + 当日面包
[更换]
```

- 只有一个项目时自动选中；
- 项目自动带入固定品牌包版本和本次业务资料；
- 页面不展开品牌、受众、资产和历史产物全集；
- 缺少当前任务必填信息时，就地提示一句并提供“补充”；
- 应用内临时修改只作用于本次 Run，不悄悄修改项目或品牌包；
- 项目保存、归档和品牌包管理留在“我的项目”和“企业资产库”，不出现在应用结果区。

### 4.3 历史记录

现有 AppRun、Artifact、ArtifactVersion 和结果历史继续作为唯一权威：

- 每次生成形成一块按时间排序的历史记录；
- 文案记录包含本次 3 条文案；
- 标题记录包含本次 6 条标题；
- 图文记录包含 1 个完整成品；
- 数字人记录包含 1 个最终视频；
- 点击详情或预览看到真实内容，不展示内部 Artifact、版本 ID、Prompt、模型名和诊断字段；
- 历史记录读取旧事实，不为了旧开发样例保留第二套生成链路。

### 4.4 操作密度

- 每个候选默认最多显示 2–3 个当前任务动作；
- 文字候选使用“复制、编辑、采用”；
- 图文和数字人成品使用“预览/播放、下载、交给发布中心”；
- 跨应用次要动作和技术诊断放入记录级“更多”，不在每条候选上重复；
- 本期不实现“喜欢/不喜欢”反馈和“生成相似”，除非后续真实使用证明它们能解决明确问题。

### 4.5 无障碍和失败反馈

- 表单项有可读 Label，不能只依赖 placeholder；
- 键盘可以完成项目、风格、素材、候选和主要动作选择；
- 焦点、错误、禁用和加载使用现有语义 Token；
- 失败提示说明用户下一步，不显示 Provider、路径、Schema 或运行 ID；
- 运行失败保留输入，用户主动选择重试；
- 付费媒体任务明确显示运行中、失败、取消和最终结果。

## 5. 门店营销文案

### 5.1 只解决一个问题

> 我这次要推广一个产品、服务或活动，帮我写出 3 条可以直接使用或轻改后使用的营销文案。

### 5.2 主路径

```text
选择项目
→ 确认本次主推
→ 补充卖点或活动（可选）
→ 选择表达风格
→ 生成 3 条文案
→ 复制、编辑或采用
```

左侧只保留：

1. 当前项目；
2. 本次主推；
3. 营销目标；
4. 卖点或活动（可选）；
5. 表达风格；
6. `生成营销文案`。

项目已有值自动带入。用户不看到项目资料全集、内容版本、风险数组、Prompt 和模型参数。

### 5.3 Prompt

营销文案使用自己的 Prompt，输入：

- 品牌和门店背景；
- 本次主推、营销目标、目标人群；
- 已确认卖点、活动、时间、价格、地址；
- 选中的风格规则和示例；
- 不允许编造的事实边界。

3 条文案分别要求：

1. 直接讲利益；
2. 放进具体消费场景；
3. 使用自然的老板或门店口吻。

Prompt 要求避免相同开头、相同 CTA、反复罗列产品名和空泛套话。差异、自然度和可用性通过真实模型输出由产品人员阅读判断，不在代码中计算分数或触发质量重试。

实现时把已经固定的项目上下文、用户当前选择和本次输入组装为一次请求；不在 Executor 中另建角度分配器、内容重写器或候选筛选器。

### 5.4 风格

复用现有 `style_presets.py` 和随代码发布的 Style Preset：

- 本阶段只调整当前预设的名称、说明、示例和 Prompt 规则；
- 普通用户只看到风格卡片和一条示例；
- 自定义参考只影响本次表达方式，不导入示例中的品牌、价格和活动事实；
- 不新增数据库、版本管理页面、运营后台或第二套 Registry。

### 5.5 输出与结果

一条记录显示 3 个完整文案卡片：

- 正文是视觉主体；
- 默认不展示角度名、风险标签、缺失事实、字数公式和预计时长；
- 编辑只编辑一段完整正文，不要求用户分别理解 hook/body/cta；
- 采用后记录选中的候选；
- 每条只显示复制、编辑、采用。

新的应用结果最小需要 `variants[].full_text`。如果字数需要展示，由应用代码从正文计算，不要求模型返回并自证。

### 5.6 文本执行器收口

在当前权威文本路径内：

- 保留 3 条非空结果、字段类型、长度上限和 JSON 结构等客观校验；
- 删除“角度不能相同”“泛化禁用词”“候选差异度”“风险标签决定失败”等主观后置校验；
- 删除由模型返回并由代码再次验证的 `word_count`、`estimated_seconds`；
- `missing_facts/risk_flags` 不再是生成成功的必需结果，也不在默认 UI 展示；
- 结构无法解析时最多进行一次结构 repair；内容普通或重复不自动 repair；
- 先确认当前打包版本和本地历史 Artifact 的真实依赖：没有真实依赖时直接更新当前结构、调用方、fixture 和测试；真实历史 Artifact 必须保持可读时，为新写入定义一个客观输出版本，现有结果历史只读旧事实，旧生成器和旧写路径在同一阶段删除。

当前 `BANNED_TERMS` 一类泛化词表不能同时充当内容质量和合规权威。只有能够对应当前正式平台规则或明确合规要求的硬规则才保留，并复用现有权威来源；没有来源的偏好词放回 Prompt 和人工发布检查，本方案不新建合规平台。

### 5.7 人工产出验收

使用一个资料完整的真实门店项目，调用当前默认模型一次。产品人员直接阅读：

- 3 条是否明显不同；
- 是否能看出是当前门店和本次活动；
- 是否使用了已有时段、人群、距离或活动事实；
- 是否出现编造事实；
- 是否至少有 2 条可以直接使用或轻改后使用。

“至少 2 条”只是一轮产品验收目标，不写进 Validator、测试 fixture 或运行时 Gate。

## 6. 爆款标题

### 6.1 只解决一个问题

> 我已经有一段内容，帮我生成 6 条不同切入方式、可以直接选择或轻改的标题。

### 6.2 主路径

```text
选择项目
→ 确认当前内容
→ 选择平台和标题目的
→ 选择风格或粘贴参考
→ 生成 6 条标题
→ 复制、编辑或采用
```

“当前内容”默认使用当前项目最近采用的营销文案。用户点击“更换”后才选择：

- 项目已有文案；
- 粘贴一段内容；
- 直接输入主题。

页面不出现“文案产物”“固定内容版本”“ArtifactVersion”等内部名称。

左侧只保留：

1. 当前内容；
2. 发布平台；
3. 标题目的；
4. 想强调的信息（可选）；
5. 标题风格；
6. `生成标题`。

### 6.3 Prompt 与风格

标题应用使用自己的 Prompt，输入当前正文、项目主推/受众/活动、平台、标题目的、风格样例和平台硬长度限制。

一次要求 6 条，从场景、人群、利益、好奇/反差、问题解决和行动引导等不同切入方式创作。方向只用于 Prompt，不要求模型返回角度、分数或风险标签。

Prompt 明确：

- 不做同义改写；
- 不把全部卖点塞进每条；
- 使用自然完整的中文；
- 不编造项目事实和夸大承诺；
- 参考标题只用于表达方式，不导入其中事实。

复用现有标题 Style Preset，不建设新的风格系统。

实现时把当前内容、项目事实、平台、标题目的、用户强调信息和风格选择组装为一次请求；不在模型返回后追加角度分类、差异度计算、候选排序或二次改写。

### 6.4 输出与执行器收口

一条记录直接显示 6 条标题，每条只有复制、编辑、采用。

新的应用结果最小需要 `candidates[].title`。标题长度由应用代码计算；平台存在明确硬限制时可以在提交边界校验。

当前文本执行器需要：

- 保留候选数量、非空字符串、类型和平台硬长度等客观校验；
- 删除 `angle`、`banned_matches`、`risk_labels` 作为生成成功条件；
- 删除标题相似度、归一化去重比例和泛化禁用词导致整批失败或 repair 的逻辑；
- 内容重复通过 Prompt 和模型优化，真实输出由产品人员判断；
- 不进行后台换模型、自动反复生成或自动筛选。

### 6.5 人工产出验收

使用真实营销文案作为默认来源，再测试一次用户粘贴内容。每次只调用当前默认模型一次。

产品人员直接判断：

- 6 条是否具有可感知的不同切入方式；
- 是否与输入内容和项目相关；
- 中文是否自然完整；
- 是否出现编造事实；
- 是否至少有 2 条值得复制或轻改；
- 自定义参考是否只模仿表达，没有导入参考商品事实。

这些结论只进入人工验收记录，不成为自动评分和测试合同。

## 7. 抖音图文

### 7.1 只解决一个问题

> 我已经有文案和门店图片，帮我制作一组可以直接预览、下载和发布的抖音图文。

### 7.2 主路径

```text
选择项目
→ 确认当前内容
→ 查看系统推荐的项目图片
→ 必要时调整图片
→ 选择页数和图文风格
→ 生成完整图文
→ 翻页预览、下载或交给发布中心
```

左侧只保留：

1. 当前内容；
2. 图文页数；
3. `已选 N 张项目图片 [查看和调整]`；
4. 图文风格；
5. `生成抖音图文`。

### 7.3 图片描述与推荐

优先复用资产库已有名称、标签、描述和图片信息。只有当前选中图片缺少可用于配图的描述时，才通过现有多模态能力生成一句客观描述。

图片描述只用于本次应用：

- 帮助从项目图片中推荐与内容相关的素材；
- 帮助分页时选择对应图片；
- 明确告诉用户缺少哪类图片。

实现边界：

- 不建立分数、阈值、向量索引或通用素材理解服务；
- 不扫描整个资产库后反复调用模型；
- 推荐结果对用户可见、可调整；
- 用户最终确认的图片是本次 Run 的固定输入。

### 7.4 分页与版式

图文 Prompt 负责：

- 第 1 页说明主题并吸引继续看；
- 中间页分别表达一个卖点、场景或活动；
- 最后一页给出行动或门店信息；
- 每页只写适合当前版式的短文案；
- 每页引用一张已确认图片。

首期只复用或完善三类明确版式：

1. 封面：主图 + 短标题；
2. 内容页：图片为主 + 短文案；
3. 行动页：活动、地址或到店信息。

版式选择只依据页面角色、图片横竖比例和文案长度等确定性信息。图片使用可靠的裁切、安全区和文字容器规则；必要时允许用户在预览中更换该页图片。

不建设主体检测、自动美学评分、版式占用率 Gate 或通用布局搜索。

### 7.5 输出与结果

每次生成显示一个成品卡：

- 真实封面；
- 标题；
- 页数；
- 预览；
- 下载；
- 交给发布中心。

点击预览直接打开完整真实页面并左右翻页。不展示分页计划、页面 Artifact、模板 ID、渲染版本和技术检查。

### 7.6 验收

使用一个资料完整、图片相关的真实项目重做咖啡样例，再选择一个不同类型的现有项目作为回归，不为验收临时建设多行业 fixture 平台。

产品人员直接查看：

- 图片是否属于当前推广对象；
- 每页图片和文字是否对应；
- 封面是否一眼看懂主题；
- 是否存在明显遮挡、裁切错误或不合理空白；
- 字体、品牌色和页面层级是否统一；
- 是否愿意直接下载或轻改后发布。

只把文件存在、页数、引用合法、渲染成功和下载可用写进自动测试；审美和相关性由可视化验收判断。

## 8. 数字人口播视频

### 8.1 只解决一个问题

> 我已经有口播内容，选择一个带默认声音的数字人，快速生成可播放、可下载、可交付发布的口播成片。

### 8.2 已完成能力直接复用

以下能力已经由 `DH-LITE-VOICE` 完成，本方案不得重新实现：

- 图片/视频场景通过同一形象选择器进入；
- 场景媒体类型自动决定图片说话或视频口型；
- 声音解析顺序为本次覆盖 → 人物默认 → 系统推荐；
- VoiceProfile、授权和音频 revision 由服务端固定；
- 字幕、封面和发布设置默认折叠；
- 结果优先显示最终视频；
- 最终平台发布按钮保持人工点击。

### 8.3 主路径

```text
选择项目
→ 确认口播内容
→ 选择数字人形象
→ 确认默认声音（必要时本次更换）
→ 生成最终视频
→ 播放、下载或交给发布中心
```

左侧默认只显示：

1. 当前项目；
2. 口播内容；
3. 数字人和场景卡片；
4. 声音摘要、试听和更换；
5. `生成口播视频`。

字幕、封面、话题和发布文案继续放在“更多设置”。

### 8.4 口播稿

数字人自己的 Prompt 把用户确认内容整理为口播稿：

- 句子短、停顿自然；
- 前几秒进入主题；
- 卖点不堆叠；
- 结尾只有一个行动；
- 保留已确认的价格、活动和门店事实；
- 不改变用户核心意思。

用户看到并编辑最终口播稿，不需要理解中间转换。

不对口播稿计算自然度、节奏分或质量分；使用真实试听和产品人员判断。

### 8.5 媒体、字幕和后期

- 继续使用当前已稳定的图片与视频工作流配置；
- 不同时运行多个 RunningHub 工作流做后台竞赛；
- 只针对真实成片中已经观察到的人物边缘、动作、口型、字幕和背景问题调整当前工作流或后期参数；
- 图片明显不适合时，用“面部太小、侧脸、头部被裁切、背景复杂”等可理解原因提示更换；
- 视频模式继续使用源视频动作、镜头和背景，不克隆源视频声音；
- 字幕继续在真实手机观看尺寸下调整字号、换行、描边/底色和底部安全区；
- Provider 失败明确停止，由用户选择重试或更换素材。

### 8.6 输出与验收

每次生成显示一个最终视频卡：

- 真实封面；
- 时长；
- 数字人名称；
- 声音名称；
- 播放；
- 下载；
- 交给发布中心。

原始音频、中间数字人片段、字幕文件和技术诊断默认隐藏。

使用当前稳定工作流分别进行一次受控图片模式和视频模式真实生成。产品人员完整观看：

- 口播是否自然且未改变事实；
- 声音是否符合人物；
- 图片模式是否存在明显静态动嘴、边缘或背景异常；
- 视频模式是否存在肉眼明显的口型提前或滞后；
- 字幕在手机尺寸是否清楚；
- 封面、视频和发布文案是否属于同一内容；
- 是否愿意把成片交给发布中心。

视觉和口型结论不写成自动评分；文件生成、媒体可读、音视频存在、字幕轨/烧录结果和 Artifact 完整性继续由自动测试保护。

## 11. 测试和真实证据

### 11.1 自动测试保护什么

- 用户从应用入口完成输入并发起真实 Run；
- 项目上下文、Style Preset、素材和声音固定正确；
- LLM 输出的客观结构和数量；
- AppRun、Artifact 和结果历史投影；
- 编辑、采用、复制、预览、下载和发布中心 handoff；
- 图文页数、文件引用、渲染和下载；
- 数字人文件、媒体可读性、声音固定、恢复和 Artifact 完整性；
- 失败、取消、重启恢复和错误提示；
- 键盘可达和关键语义 Label。

### 11.2 自动测试不保护什么

不把以下结论写进 fixture、Validator、测试 Gate 或运行时合同：

- 文案是否高级、有感染力或至少两条好用；
- 标题是否爆款、足够不同或值得点击；
- 图片是否“好看”；
- 版式是否有审美；
- 数字人动作是否丰富；
- 逐音节口型是否自然。

这些使用真实结果和人工评审。

### 11.3 每个应用的最小证据

每个 Stage 至少保留：

- 定向自动测试结果；
- Desktop production build 或该阶段约定的构建结果；
- 一条完整主路径截图序列；
- 一次真实结果的可读、可翻页或可播放证据；
- 产品人员的简短产出结论；
- 独立六维评审结论和修复复验依据。

数字人和图文的媒体证据必须来自本阶段实际生成的文件；旧截图只能说明历史问题，不能代替本阶段验收。

## 12. 风险、失败与回滚

### 12.1 当前需要处理的失败

- 未配置 LLM：提示到系统设置，不发起 Run；
- 项目缺少当前必填内容：就地说明缺少什么；
- Provider 超时或失败：停止并保留输入，由用户主动重试；
- 图文没有合适图片：提示缺少的图片类型并打开资产选择；
- 媒体素材不适合数字人：用普通语言说明原因并允许更换；
- 图文或视频生成中取消、重启：继续使用现有 AppRun/任务恢复，不新建状态机；
- 发布中心 handoff 失败：保留已完成 Artifact，不重新生成内容。

其他低概率、低损失情况清楚失败，不增加主流程分支。

### 12.2 回滚

- Prompt、Style Preset、页面和模板使用普通代码版本回滚；
- 不删除已有 Project、AppRun、Artifact 和历史结果；
- 不通过永久保留 V1/V2 两套生成代码实现回滚；
- 如阶段使用现有临时 rollout flag，必须在 `APP-BIZ-5` 删除或登记有真实证据的短期观察窗口；
- 外部 Provider、媒体文件和发布中心保持现有边界。
