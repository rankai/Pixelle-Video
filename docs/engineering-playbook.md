# Pixelle 工程实践手册

> 状态：解释性参考，不是需要逐条执行的门禁清单。
>
> 强制核心规则见 [`development-principles.md`](development-principles.md)。本手册保留详细边界、案例、目录示例和判断依据；开发者只需按当前变更读取相关章节，不要求低风险修改每次通读全文。若本手册与核心规则、Accepted ADR 或明确产品决策冲突，以核心规则中定义的优先级为准。

## 原理摘要

本手册解释核心规则的判断依据和实践边界，不是需要在运行时实现的治理框架。日常开发先遵守 [`development-principles.md`](development-principles.md)；以下内容用于理解其来源：

1. 从当前真实问题和根因出发，不从熟悉的技术方案反推需求；
2. 选择职责正确、能够完整解决问题的最低复杂度方案；
3. “最小”不能牺牲单一权威、架构边界、安全、数据一致性和明确失败；
4. 用户可见功能按纵向闭环交付，不合入假成功、无调用者或不可达的核心代码；
5. 主观质量由业务、模型、Prompt、素材、模板和用户判断解决，不建设伪精确的质量合同；
6. 没有当前事实依据，不增加平台、状态、分支、兼容层或未来系统；
7. 临时兼容和发布切换必须单一权威、可观察、可删除，不能层层叠加；
8. 方案、测试、评审和恢复投入与风险相称，小改动不套用重流程，高风险边界不为速度让步。

默认开发节奏：

```text
守住工程底座
→ 先复用项目已有且语义匹配的能力，再使用当前技术栈和成熟框架
→ 选择职责正确的最低复杂度实现
→ 交付完整纵向闭环
→ 观察真实使用和维护压力
→ 达到明确触发条件后演进架构
→ 完成迁移并删除旧路径
```

Pixelle 默认采用：

> 敏捷纵向交付 + 持续设计 + 模块化单体 + Feature-first + 语义化 Design Token + 只用于真实边界的 Ports/Adapters。

这套组合是工程方向，不要求为每个功能建立完整分层、接口、目录和 Adapter。架构元素只在当前职责和边界需要时出现。

详细条款用于解释边界，不应被转化成新的合同平台、评分系统或运行时门禁。

## 1. 适用范围

本手册可用于解释 Pixelle 项目的以下工作：

- 产品功能；
- UI 与交互；
- 后端服务；
- 数据模型；
- AI 与媒体能力；
- 自动化任务；
- 测试、部署和运维；
- 重构与架构演进；
- 实施方案和代码评审。

它帮助理解“如何做开发决策”，不是一个需要在运行时实现的框架，也不是要求逐条打勾的评审清单。

所有新功能和重构遵循核心开发原则；存在安全、合规、数据一致性要求或 Accepted ADR 时，同时遵守对应的更具体约束。

本文件中的关键术语：

- **当前真实问题**：已批准需求、可复现缺陷、真实运行事故、当前用户反馈，或能够明确说明影响的安全、数据和外部协议风险；
- **当前调用方**：当前代码或已批准阶段中真实存在并会使用该能力的页面、服务、任务、客户端或外部系统；
- **已确认演进方向**：已进入明确阶段并有时间、所有者和调用方，或已由 Accepted ADR 作出具体决定的变化；
- **高损失风险**：可能造成安全、隐私、权限、资金、数据丢失、不可逆外部操作或重大业务中断的风险；
- **所有者**：对能力演进、故障处理和删除负责的明确人员、团队或模块责任方。

## 2. 核心原则

> 从当前真实问题出发，先找到根因，再使用能够解决问题的最小充分方案；没有经过真实重复验证的共性，不提前抽象。

“完整、先进、可扩展、智能化”本身不是开发理由。

一项能力只有在解决当前真实问题时才有价值。未来可能使用、理论上更通用、架构看起来更完整，不能单独构成立项依据。

“最小充分”不是最低成本、最少代码或只保证当前演示能运行。它必须同时满足当前功能所需要的：

- 正确性；
- 稳定性；
- 安全性；
- 可维护性；
- 与已确认演进方向相称的扩展边界；
- 与风险相称的测试、恢复和可观察性。

本原则反对的是没有现实依据的复杂度，不反对必要的工程质量投入。

## 3. 开发前必须回答的问题

任何功能、重构或机制在实施前，都必须用与风险相称的变更说明回答：

1. 当前是谁遇到了什么问题？
2. 这个问题实际造成了什么影响？
3. 已有实现为什么不能满足？
4. 已确认的根因是什么？
5. 最小的有效修改是什么？
6. 用户操作或系统行为会怎样变化？
7. 如何用真实结果证明问题被解决？
8. 本次明确不做什么？

如果这些问题没有回答清楚，不进入实现。

不要求所有改动都编写独立方案文档。按风险分级执行：

- **低风险小改**：用简短说明写清问题、根因、修改和验证即可，例如文案、间距、局部样式和不改变业务语义的小修复；
- **普通功能**：使用轻量纵向闭环方案，覆盖上述八个问题；
- **高风险变更**：涉及架构边界、安全、权限、持久化、数据迁移、支付、不可逆外部操作、跨进程协议或新基础设施时，必须使用完整实施方案；形成长期架构决策时同步编写或修订 ADR。

风险分级用于减少无价值流程，不允许把高风险变更拆小后按低风险处理。

不得用以下内容替代问题定义：

- “提高质量”；
- “增强扩展性”；
- “完善闭环”；
- “统一能力”；
- “为未来做准备”；
- “行业最佳实践”；
- “建立平台化基础”。

这些可以是结果，但不能作为没有具体用户问题的开发起点。

## 4. 先判断根因，再选择手段

不得从熟悉的技术方案反推问题。

例如，结果不好不等于需要评分系统；运行失败不等于需要状态机；两个页面相似不等于需要平台组件；未来可能有多个调用方不等于现在需要中台。

先把问题归入真实根因：

- 信息不完整；
- 业务流程不合理；
- 文案或模型能力不足；
- UI 信息组织不清；
- 数据边界错误；
- 外部服务不稳定；
- 媒体工作流或模板效果不足；
- 重复操作确实造成成本；
- 安全、恢复或一致性存在风险。

解决方案必须直接对应根因。

---

## 5. 默认采用最小充分方案

默认从较低复杂度向较高复杂度评估：

```text
复用项目已有且语义匹配的实现
→ 使用当前技术栈、标准库或成熟框架能力
→ 修正现有配置或内容
→ 修改局部逻辑
→ 扩展现有组件或服务
→ 新增当前功能自己的模块
→ 抽取共享能力
→ 新建平台、引擎或基础设施
```

这不是强制实现顺序。应选择第一个能够完整解决问题、同时保持职责边界和单一权威的层级。

如果局部修改虽然技术上可行，却会继续扩大巨型组件、把业务逻辑堆进路由或页面、复制核心规则、制造多权威或循环依赖，应直接在当前功能内建立职责清楚的小模块。不得为了少新增文件而破坏架构。

“最小”不是少写代码，而是：

- 用户新增的理解成本最小；
- 新增的状态和数据源最少；
- 对现有链路的影响范围最小；
- 需要长期维护的机制最少；
- 回滚和替换成本可控；
- 足以解决当前问题。

---

## 6. 局部解决优先于全局抽象

一个功能的问题默认在该功能内部解决。

只有满足以下条件时，才考虑抽取共享能力：

1. 同类问题已经在多个独立场景真实出现；
2. 各场景对该能力的定义、输入和行为基本稳定；
3. 局部实现已经造成可观察的重复、冲突或维护成本；
4. 抽象后的接口比保留局部实现更简单；
5. 已有当前调用方，不以假设中的未来调用方作为主要依据。

默认遵循“重复三次再抽象”的经验规则。安全、权限、数据一致性和外部协议边界可以例外，但必须说明原因。

“重复三次”只适用于尚未稳定的候选复用模式，不适用于同一个业务事实或权威规则。同一份权限、计费、状态归属、持久化事实和安全规则从第一次出现起就必须只有一个所有者；不同功能不得各自复制一份。

共享视觉样式、基础控件和稳定数据边界，不等于共享业务逻辑。

### 6.1 职责拆分不等于公共抽象

“不过度抽象”不等于“不建设架构底座”；“没有三个调用方”也不等于不能拆函数、拆组件、拆文件。

以下拆分用于保持当前代码职责清楚，即使暂时只有一个调用方也可以实施：

- 把一个页面拆成职责独立的输入区、结果区、选择器、弹窗和状态组件；
- 把状态、副作用和异步流程拆进当前功能自己的 Hook、Model 或 Service；
- 把业务规则从 UI、Router、脚本入口和启动文件移入当前领域模块；
- 把 API 调用、数据转换和持久化访问移入当前功能自己的 Client、Service 或 Repository；
- 把功能样式移入当前功能自己的样式文件；
- 把过长函数按真实业务步骤拆成可命名、可测试的局部函数。

这些内部模块默认留在当前 feature 或 domain，不因为拆出来就放进 `shared`、`common`、`core` 或全局容器。

只有准备建立跨功能公共依赖时，才适用本节的多调用方、稳定语义和“重复三次”判断。

### 6.2 复用与新增的判断顺序

开发功能或页面前，按以下顺序检查：

```text
项目已有且语义匹配的能力
→ 当前技术栈、标准库或成熟框架已有能力
→ 当前 feature/domain 内新增职责清楚的实现
→ 多个真实场景稳定后再提升为共享能力
```

复用必须以语义和行为匹配为前提，不能只因为名称相似或少写代码就强行复用。如果复用现有函数或组件需要不断增加布尔参数、调用方判断和特殊分支，应重新判断职责边界，而不是继续扩大错误抽象。

为代码可读性提取一个局部函数、为页面拆出一个单用途组件，与建设通用函数库或公共组件库不是同一件事。

### 6.3 Design Token 和公共 UI 的边界

以下稳定的产品语义可以从第一次出现时进入统一主题或设计底座：

- 品牌主色、文字色、背景、边框和状态色；
- 字体层级、圆角、阴影、间距和页面容器规则；
- 按钮、Tab、状态 Tag、表单和反馈的统一产品语义；
- 无障碍、禁用、错误和焦点状态。

只在单个页面使用的装饰、插画、渐变和特殊布局默认留在功能内。两个 CSS 值偶然相同不构成 Design Token；Token 必须表达稳定语义，而不是记录某个页面的具体像素。

基础控件优先使用当前 UI 框架。只有产品语义、交互或视觉规则真实重复时，才建立 Pixelle 公共组件；不得重新实现成熟框架已经可靠提供的 Button、Select、Modal、Form 等基础能力。

## 7. 合同、Schema 和状态机的使用边界

合同机制用于保护客观边界，例如：

- 外部 API；
- 前后端数据结构；
- 数据持久化；
- 文件和媒体引用；
- 权限和租户隔离；
- 支付、订单和资金；
- 幂等、恢复和并发；
- 不可逆或高风险操作；
- 多个真实实现必须共同遵守的稳定协议。

合同机制不用于替代主观业务判断，例如：

- 内容是否有感染力；
- 页面是否好看；
- 表达是否自然；
- 创意是否足够好；
- 用户是否喜欢；
- 模型结果是否“高级”。

主观结果应通过业务设计、模型、Prompt、素材、模板、真实用户评审或人工决策解决。

新增合同前必须说明：

- 它保护的具体边界；
- 不使用合同会发生什么确定性错误；
- 当前有哪些生产者和消费者；
- 谁负责版本演进和兼容。

生产者和消费者不要求各有多个；一个真实的持久化、跨进程、外部输入或信任边界也可以成立。普通函数参数、局部类型和为了代码可读性使用的数据类，不自动构成需要版本治理的“平台合同”。

`schema`、`validator` 和 `repair` 只能处理机器可验证的结构与协议错误，例如字段缺失、类型错误、枚举非法和格式损坏。它们不得用于给标题、文案、画面或创意做主观质量判定，也不得因为主观结果“不够好”自动重试。

回答不出来时，不新增合同。

## 8. 自动化的使用边界

一项操作只有同时满足以下条件，才适合自动化：

- 规则明确；
- 输入和成功结果可以观察；
- 失败能够停止或恢复；
- 重复频率足以产生真实收益；
- 自动化不会掩盖用户应当作出的业务选择；
- 维护成本低于人工成本。

自动重试只适用于可确认的暂时性技术失败，并且必须：

- 有明确失败原因；
- 操作幂等或不会产生重复副作用；
- 次数有限；
- 可观察、可停止；
- 不会造成不可控费用。

主观结果“不够好”不是自动重试的理由。应让用户明确选择重新生成、修改输入、更换方式或接受当前结果。

---

## 9. 评分和智能决策的使用边界

不得因为某个结果难评价，就默认增加评分。

引入评分或自动决策前必须证明：

- 评分对象可以被稳定定义；
- 有可信的真实样本或人工结论可用于校准；
- 分数高低会触发明确、合理的动作；
- 错误评分的后果可接受；
- 用户或运维人员能理解最终决定；
- 分数比直接规则或人工判断更有价值。

如果分数只能生成一个看似精确的数字，却不能可靠指导行动，就不应实现。

---

## 10. 不为未确认的未来提前建设

未来需求只有满足以下任一条件时，才进入当前设计：

- 已经在批准的路线图中；
- 已有明确时间、负责人和调用方；
- 当前方案如果不保留边界，将造成高成本或不可逆迁移；
- 属于必须提前满足的安全、合规或数据隔离要求。

“批准的路线图”必须已经进入明确阶段，并能指出时间或阶段、所有者和真实调用方。愿景、讨论记录、普通待办、竞品可能会做或“以后也许需要”都不构成已确认演进方向。

对于其他未来可能：

- 可以在文档中记录；
- 可以保留清晰代码边界；
- 不提前创建数据库、服务、管理后台、消息系统或通用引擎；
- 不增加当前用户的操作步骤。

“保留未来扩展空间”优先通过模块边界和命名实现，而不是提前实现未来功能。

---

## 11. UI 和用户操作复杂度

每增加一个用户可见字段、按钮、步骤、状态或配置，都必须说明：

- 用户为什么必须理解它；
- 系统为什么不能自动使用可靠默认值；
- 它是否属于当前主任务；
- 不展示它会造成什么问题。

默认处理方式：

- 稳定默认值由系统自动使用；
- 低频项放入“更多设置”；
- 技术信息放入诊断或日志；
- 管理操作留在对应管理页面；
- 当前页面只展示完成当前任务所需的内容。

不能把后端的数据结构直接映射成前端表单，也不能把系统内部流程当作用户操作流程。

---

## 12. 新基础设施和新机制的成本说明

新增以下能力时必须单独说明必要性：

- 新数据库或新数据源；
- 新服务或新进程；
- 队列、缓存或消息系统；
- 插件平台；
- 规则引擎；
- 工作流引擎；
- 通用评分系统；
- 通用配置中心；
- 大范围状态机；
- 双写、迁移和兼容层。

方案必须写明：

- 当前问题；
- 为什么现有能力无法解决；
- 当前调用方；
- 新增的状态和维护责任；
- 失败和回滚方式；
- 不建设它的现实代价。

收益不能证明高于复杂度时，维持现有实现。

---

## 13. 真实结果优先于交付数量

完成不能只依据：

- 新增了多少文件；
- 增加了多少 Schema；
- 测试数量；
- 文档数量；
- 架构是否完整；
- 所有内部状态是否覆盖。

验收必须回到最初问题：

- 用户是否能更顺利地完成任务；
- 实际结果是否改善；
- 原问题是否可以稳定复现并确认已解决；
- 是否引入新的理解或维护成本；
- 是否保留必要的失败、恢复和安全边界。

测试和文档用于证明实现，不是实现价值本身。

---

## 14. 方案评审的停止问题

评审任何方案时，依次询问：

1. 如果不做，会发生什么现实问题？
2. 能否通过修改现有逻辑解决？
3. 是否把一个局部问题扩大成了全局系统？
4. 新增的每个状态、表、接口和配置是否有当前使用者？
5. 是否用技术机制替代了本应由产品、内容或人工完成的判断？
6. 用户是否被迫理解系统内部概念？
7. 是否为了极少发生的情况增加了主流程复杂度？
8. 验收证明的是用户问题解决，还是只证明机制运行？

任一问题暴露出范围扩大时，先缩减方案，再进入实现。

---

## 15. 允许例外的情况

以下情况可以在问题尚未重复三次前建设稳定边界：

- 认证和权限；
- 隐私和安全；
- 财务、支付和订单；
- 数据丢失风险；
- 不可逆操作；
- 并发写入和幂等；
- 第三方外部协议；
- 跨进程或跨服务通信；
- 法律、合规和审计要求；
- 已接受 ADR 明确要求的架构边界。

例外只允许解决对应风险，不能借机扩大到无关平台建设。

---

## 16. 极小概率场景与分支控制

不能因为“理论上可能发生”，就在主流程中不断增加分支。

新增异常分支、兜底逻辑、兼容路径或降级路径，至少需要满足以下一项：

- 已在真实运行中发生；
- 是当前批准需求明确要求支持的场景；
- 如果发生会造成安全、隐私、支付、数据丢失或不可逆后果；
- 属于必须遵守的外部协议或法律要求。

对于低概率且低损失的场景，默认处理方式是：

```text
停止当前操作
→ 给出清楚错误信息
→ 保留必要日志
→ 允许人工恢复或重新操作
```

不要为了让所有理论情况都“自动继续”而增加隐藏分支。

如果安全 fallback 比报错路径更简单，并且同时满足以下条件，可以使用：

- 行为对用户或调用方可理解，不伪装成原目标成功；
- 不产生第二个权威来源或长期执行路径；
- 不隐藏需要修复的上游错误；
- 不增加新的持久化状态、重复副作用或不可控费用；
- 有必要日志或结果说明。

每个会改变业务结果、状态、安全结论或外部副作用的新增分支必须同时具备：

- 明确触发条件；
- 明确用户或系统影响；
- 对应的真实需求、事故或风险说明；
- 与风险相称的验证证据；
- 清楚的失败结果，不能静默吞错。

验证证据可以是单元测试、集成测试、受控 fixture、真实运行或明确的人工验收。一个测试可以覆盖多个相关分支；不要求为每个普通防御性条件单独创建测试。

以下做法默认禁止：

- 为无法说明概率和影响的假设场景增加分支；
- 使用层层 fallback 掩盖上游数据或设计错误；
- 捕获所有异常后返回看似成功的结果；
- 为同一任务长期维护多条行为近似的执行路径；
- 为了兼容未知未来客户端预留当前没有调用者的判断；
- 在多个下游重复判断同一脏数据，而不修复数据来源。

风险处理必须与影响相称：

- 极低概率但会造成重大损失：建立必要保护；
- 高频但影响较小：直接简化主流程；
- 极低概率且影响较小：清楚失败，不建设复杂自动处理。

---

## 17. 禁止半实现和断头代码

一项功能应以可使用的纵向闭环交付，而不是分别堆积接口、Schema、按钮和占位实现。

完整纵向闭环至少包括：

```text
真实入口
→ 有效输入
→ 实际业务处理
→ 用户可见或系统可消费的结果
→ 明确失败处理
→ 对应测试与实际运行验证
```

以下情况不得作为完成的生产功能合入：

- 页面有按钮，但没有真实处理能力；
- 后端有接口，但没有当前调用者；
- 已定义 Schema，但运行链路不读写它；
- 已创建 Adapter、Repository 或 Service，但没有真实入口；
- 返回固定成功、假数据或占位结果；
- 只实现创建，没有查询、继续或完成路径；
- 只实现正常路径，没有当前已知的必要失败处理；
- 旧流程和新流程同时存在，但没有明确切换和删除计划；
- 使用 `TODO`、空函数或临时分支代表核心业务尚未完成，却将阶段标为完成。

如果一个阶段不能交付完整纵向闭环，应在自然边界停止：

- 只提交方案或原型；
- 只提交独立实验；
- 只提交不可见的基础改动；
- 不把未接通部分暴露给用户；
- 不宣称目标功能已经完成。

阶段性代码只有在确实必须提前合入时，才允许使用默认关闭的 feature flag 隔离，并必须写明：

- 当前为什么需要提前合入；
- 哪个后续阶段负责接通；
- 负责人或所有者；
- 完成或删除条件；
- 最迟复查时间。

本节所指的是用于提前合入、发布观察、迁移或新旧切换的临时 `Rollout/Migration Flag`。它不能长期替代完成实现，也不能成为保留无用代码的理由。

长期存在的 `Product/Policy Flag` 用于真实产品能力、套餐权益、管理员策略或安全确认边界，可以不设删除时间，但必须有：

- 稳定且用户或运营能够理解的业务语义；
- 明确所有者；
- 默认值和权限边界；
- 覆盖启用与关闭行为的测试；
- 单一权威实现，不能借开关长期保留两套近似业务逻辑。

---

## 18. 分支、状态和兼容代码必须可追溯

每一个新增的以下元素都必须能追溯到当前事实：

- `if/else` 业务分支；
- 状态和状态迁移；
- 数据表和字段；
- API 和事件；
- 重试与降级；
- 兼容层和 Adapter；
- feature flag；
- 后台配置；
- 用户可见选项。

可接受的事实来源包括：

- 当前批准需求；
- 可复现缺陷；
- 真实生产事故；
- 已接受 ADR；
- 外部协议；
- 安全、合规或数据风险。

如果无法指出它服务的当前场景，就应删除或不实现。

兼容层、双写、旧版路径和临时 feature flag 必须有：

- 引入原因；
- 当前调用方；
- 观察窗口；
- 删除条件；
- 删除负责人。

观察窗口结束且旧路径不再需要时，应删除旧代码，不能让 V1/V2、legacy/new 和 temporary/final 永久并存。

## 19. 兼容不是默认要求

旧代码、旧接口、旧 Schema、旧测试或旧文档仍然存在，不等于必须兼容。

两个仍被正式支持的产品模式、套餐能力或部署形态同时存在，不自动构成兼容层。例如本地桌面模式与未来云端模式可以各自是正式产品能力；只有旧字段转换、旧接口转发、旧数据读取和新旧运行路径切换属于兼容问题。

兼容层只有同时满足以下条件时才允许新增：

1. 有当前真实用户、已发布客户端、外部调用方或真实持久化数据依赖旧行为；
2. 无法在同一次受控切换阶段或同一发布周期内安全完成调用方升级或数据迁移；
3. 直接切换造成的现实损失明显高于临时兼容的复杂度；
4. 已明确新旧权威、观察窗口、删除条件和负责人。

“同一次受控切换”不要求所有代码位于同一个 commit 或 PR。迁移准备、数据迁移、切换和清理可以分批提交，但必须属于同一个有明确终点、不中断单一权威的迁移计划。

以下对象不构成兼容理由：

- 尚未正式发布的草稿接口；
- 仅供当前开发使用的 fixture；
- 已经过时的测试断言；
- 没有真实调用者的旧方法；
- 为旧实现编写的内部文档；
- “以后也许有人会用”的假设调用方；
- 为了少修改几个当前调用点而保留的旧入口。

处理旧实现的优先级固定为：

```text
更新当前调用方并直接切换
→ 一次性迁移真实数据
→ 使用明确版本边界完成短期切换
→ 最后才考虑临时兼容层
```

对本地桌面数据，优先使用：

```text
备份
→ 一次性迁移
→ 验证
→ 运行时只保留新结构
```

不得为了避免迁移，在每次读取和写入时永久判断新旧格式。

### 19.1 单一权威

新旧实现并存期间必须明确哪一方是唯一权威。

默认禁止：

- 新旧双写但没有对账和结束时间；
- 先读新、失败读旧、再回写新的无限循环；
- 多层 Adapter 互相调用；
- V1 调 V2、V2 再回退 V1；
- 新状态机和旧状态机同时决定业务状态；
- 新旧页面、接口和任务流都可以修改同一份业务事实；
- 在已有兼容层外再叠加一层兼容层。

如果需要在兼容层上继续增加兼容层，应停止实现，重新制定一次性迁移和切换方案。

### 19.2 兼容必须与删除同时设计

临时兼容层在创建时必须同时登记：

- 当前真实依赖者；
- 兼容的准确行为；
- 新实现的唯一权威；
- 观察窗口；
- 最迟删除阶段或日期；
- 删除前需要满足的证据；
- 删除负责人。

缺少任何一项，不新增兼容层。

功能完成时应满足以下二选一：

1. 旧路径已经删除；
2. 存在经过明确批准、仍在观察窗口内的临时兼容例外。

“新功能已实现，但旧路径以后再清理”不能标记为完成。

### 19.3 回滚不等于永久保留旧代码

回滚优先依靠：

- 版本化发布包；
- 数据备份；
- 可逆迁移；
- feature flag 的短期发布切换；
- 明确的发布回退步骤。

不能把永久保留整套旧业务实现当作默认回滚方案。

用于发布观察、迁移和兼容切换的 `Rollout/Migration Flag` 必须有删除时间，不能让两套实现无限期共存。具有稳定业务语义的 `Product/Policy Flag` 按第 17 节管理，不属于临时兼容机制。

为了审计、历史查看、回滚证据或数据迁移而保留旧事实和旧版本记录，不等于保留旧运行时代码。没有真实调用方时，应保留必要数据并删除旧执行路径，而不是让历史数据成为永久兼容理由。

### 19.4 控制清理范围

发现历史兼容垃圾时，不自动启动全仓库大重写。

正确处理方式：

- 立即停止继续增加新的兼容层；
- 只清理当前功能实际触达的旧路径；
- 先确认真实调用方和真实数据；
- 在当前纵向闭环内完成切换和删除；
- 与当前任务无关的历史代码单独登记，不顺手扩大范围。

这样既避免继续堆积，也避免“开发一周、全量清理一周、核心功能仍未交付”。

## 20. 每份实施方案的最小模板

普通功能和高风险变更的实施方案至少包含：

```text
当前问题
真实用户或系统影响
根因
最小解决方案
用户体验变化
实现范围
明确不做
真实验收方法
风险与回滚
低概率场景如何处理
是否存在阶段性或未接通代码
是否涉及旧代码、旧数据或旧调用方
若需兼容，真实依赖者、唯一权威和删除条件是什么
```

低风险小改不要求套用完整模板，按第 3 节保留简短变更说明即可。不得为了形式完整，把同一个事实重复写入多份方案、合同和台账。

除非当前问题确实需要，否则方案不必固定包含：

- 新 ADR；
- 新 Schema；
- 新状态机；
- 新评分；
- 新队列；
- 新迁移；
- 新管理后台；
- 新通用平台。

---

## 21. 功能完成定义

只有同时满足以下条件，功能才可以标记为完成：

- 目标用户或系统可以从真实入口进入；
- 主任务可以走到真实结果；
- 结果可以被查看、保存、消费或继续交付；
- 当前已知的必要失败可以被用户理解或被系统明确记录；
- 涉及持久化或长任务时，重启后的行为符合需求；
- 关键逻辑有针对性测试；
- 已按风险比例完成一次真实运行验证；
- 页面、接口、数据结构和实际行为一致；
- 没有本功能引入的不可达核心代码、占位成功或未说明的永久分支；
- 旧路径已经删除，或仍处于经过批准且有明确截止时间的兼容观察窗口。

如果真实验证必须等待用户授权、第三方账户、付费资源、生产窗口或不可逆人工确认，可以标记为“实现完成，等待外部验收”，但不能标记为“功能可用”或使用模拟结果代替真实证据。等待期间应明确缺少的证据和后续验收入口。

以下内容可以被标记为“已完成的阶段交付”，但不能被标记为“功能完成”：

- 方案；
- 原型；
- 数据迁移准备；
- 接口草稿；
- 基础组件；
- 实验；
- 默认关闭且尚未接通的能力。

评审发现半实现、无调用者代码或无法到达的核心路径时，结论必须是“未完成”或“阶段边界完成”，不能用测试数量、合同齐全或构建成功代替。

---

## 22. 不过度设计不等于降低工程质量

简单设计的目标是减少概念、状态、分支和维护负担，不是牺牲正确性、稳定性、安全性或长期可维护性。

以下投入默认属于必要工程质量，不应被当作过度设计：

### 22.1 清晰架构边界

- 业务逻辑不堆在路由、页面或脚本入口中；
- 模块有明确职责和数据所有权；
- 外部 Provider、文件系统、数据库和 UI 之间有清楚边界；
- 同一业务事实只有一个权威来源；
- 高变化实现与稳定领域逻辑适当隔离；
- 当前已经确认的替换点保留清晰接口。

清晰边界可以通过小模块、明确函数和稳定接口实现，不等于提前建设中台、插件系统或微服务。

### 22.2 代码质量

- 命名表达真实业务含义；
- 核心函数职责单一；
- 错误处理明确，不静默吞错；
- 资源能够正确释放；
- 不复制业务状态和核心规则；
- 测试覆盖关键行为而不是只覆盖实现细节；
- 删除失效代码和无调用者代码；
- 注释解释原因和边界，不复述代码。

为了快速交付而加入难以理解的条件嵌套、复制粘贴和临时成功返回，同样属于应被拒绝的复杂度。

### 22.3 稳定性

根据当前功能风险，必要时必须考虑：

- 超时和取消；
- 并发写入；
- 幂等和重复提交；
- 长任务重启恢复；
- 事务和数据一致性；
- 外部服务失败；
- 文件损坏和资源释放；
- 清楚的错误提示和必要日志。

不是每个功能都需要完整状态机、队列或恢复系统。只有长任务、外部副作用、持久化写入或高损失操作需要相应机制。

### 22.4 安全性

安全不是可选优化。涉及相应边界时必须做到：

- 密钥和凭证不进入日志、前端或长期证据；
- 不信任外部输入、客户端路径和第三方返回；
- 文件访问限制在可信目录；
- 权限遵循最小授权；
- 高风险操作有明确确认边界；
- 用户数据、租户数据和外部调用保持隔离；
- 依赖和外部服务使用已知安全配置。

安全措施应针对真实威胁边界，不能以安全名义无限扩大到无关平台建设。

### 22.5 扩展性

扩展性优先通过以下方式保留：

- 清晰模块边界；
- 依赖方向稳定；
- 外部能力通过窄接口接入；
- 数据结构具备明确版本语义；
- 避免把供应商实现写入领域逻辑；
- 避免把当前 UI 结构固化为领域模型；
- 对已经确认的近期变化保留替换点。

扩展性不等于提前实现未来功能。可以保留一个清晰接缝，但不提前创建未来的数据库、服务、管理页面、配置和分支。

### 22.6 可观察性和性能

- 关键失败要有足够日志定位原因；
- 长任务需要可见进度和最终结果；
- 外部调用需要记录非敏感身份和失败类型；
- 性能问题以测量结果为依据；
- 对真实主流程设置合理响应和资源目标。

不因为需要几条关键日志就建设完整监控平台，也不因为担心未来性能就提前引入缓存、队列或分布式架构。

### 22.7 风险相称原则

工程投入应由“发生概率 × 影响程度 × 恢复难度”共同决定：

| 情况 | 默认处理 |
| --- | --- |
| 高频、高影响 | 完整设计、测试、恢复和观察 |
| 低频、高影响 | 必要保护、明确停止和可靠恢复 |
| 高频、低影响 | 简单直接地优化主流程 |
| 低频、低影响 | 清楚失败或人工处理，不增加复杂自动化 |

安全、支付、数据丢失、权限和不可逆操作，即使低频也需要可靠保护。

### 22.8 架构投入的判断标准

架构投入满足以下任一条件时通常合理：

- 消除当前已经存在的多权威或数据冲突；
- 保护安全、支付、权限、持久化或不可逆边界；
- 支撑当前确定的多个调用方；
- 隔离当前已经存在的外部供应商变化；
- 解决已经测量到的性能或稳定性问题；
- 显著降低当前功能的理解和维护成本；
- 避免已经确定的近期演进造成高成本重写。

如果架构投入主要服务假设中的远期场景，或新增的概念、状态和维护责任多于它消除的复杂度，就应缩减。

出现以下任一事实时，应主动进行架构调整评审，不能继续用“避免过度设计”推迟必要重构：

- 同一业务事实出现多个权威来源；
- 一个模块同时承担多个独立业务职责，并持续增长；
- 同类变更反复跨越多个层级或修改大量无关文件；
- 核心业务规则被复制；
- 依赖方向混乱、出现循环依赖或 Provider 细节进入领域逻辑；
- 测试、发布、排障或新人理解成本持续上升；
- 当前多个真实调用方已经需要稳定边界。

评审只解决已经出现的结构压力，不借机重写与当前问题无关的全仓库代码。

### 22.9 评审平衡问题

评审不能只问“是不是做多了”，还必须问：

1. 最小方案是否仍然正确、安全、稳定？
2. 是否为了少写代码把业务逻辑堆在错误层级？
3. 是否产生新的单点、数据不一致或不可恢复风险？
4. 当前已确认的变化能否在清晰边界内完成？
5. 代码是否容易理解、测试、替换和删除？
6. 删除某项工程投入后，节省的复杂度是否大于新增风险？

只有同时通过“没有过度设计”和“没有牺牲工程质量”两方面评审，方案才可以进入实现。

### 22.10 技术探索与 Spike

存在真实技术不确定性时，可以先进行时间受控的实验，而不是直接把猜测设计成生产架构。实验必须：

- 写清需要回答的问题或假设；
- 设定时间范围和停止条件；
- 与正式运行路径和真实数据隔离；
- 记录能够支持决策的结果；
- 结束后删除实验代码，或按生产标准重新实现并接入真实纵向闭环。

实验成功不等于生产功能完成。不得把实验脚本、临时依赖、假数据或绕过安全边界的实现直接演变成长期产品代码。

### 22.11 成熟框架、项目约定与应用骨架

本节总结的原则可见于 Laravel 等成熟框架，但 Pixelle 当前使用 React、Tauri、FastAPI 和 Python。Laravel 仅是工程思想的参考来源之一，不是项目依赖、目标架构、目录规范或迁移方向。Pixelle 借鉴的是“提供一条清楚、低决策成本的默认开发道路”，不复制其语言、Facade、Active Record 或框架魔法。

#### 22.11.1 约定优于自由发挥

同类功能默认使用统一的：

- 目录和命名；
- 依赖方向；
- 输入校验和错误表达；
- 配置与服务装配入口；
- 主题 Token 和基础组件；
- 测试入口和真实验收方式。

开发者可以因真实业务需要偏离约定，但必须说明默认结构为什么不能满足。约定持续造成重复绕行时，应修订约定，不能让错误结构以“一致性”为理由永久存在。

#### 22.11.2 Feature-first 与模块化单体

前端优先按用户功能组织代码，后端优先按业务领域和数据所有权组织代码。页面、Router、脚本和启动入口负责组合，不承载核心业务。

推荐的前端自然边界：

```text
features/<feature>/
├── components/
├── model/
├── api/
├── hooks/
├── styles/
└── tests/
```

这是可选示例，不是固定脚手架。测试可以与源码共置，也可以放在 feature 自己的测试目录；不得只为匹配示例迁移现有目录。

推荐的后端自然边界：

```text
<domain>/
├── models
├── service
├── repository
├── ports       # 只在存在真实外部边界时
└── errors
```

目录和文件名同样只是自然边界示例。不得把一个领域的所有逻辑固定堆进单个 `service.py` 或 `repository.py`；出现多个用例、聚合、数据所有权或独立副作用时，应沿真实职责继续拆分。

目录按当前需要创建，不为了看起来完整而生成空目录、空接口和占位文件。一个小功能可以只有两三个文件；一个复杂功能应按职责继续拆分。

模块化单体要求边界清楚、进程内调用直接、业务事实单一权威。它不要求提前拆微服务、微前端、独立数据库或消息系统。

#### 22.11.3 依赖装配和 Ports/Adapters

依赖在明确的组合根集中装配，例如应用启动、FastAPI dependency provider 或 Tauri 启动层。业务代码显式声明需要的依赖，不在任意位置查找全局 Service、创建数据库连接或解析 Provider 配置。

Ports/Adapters 只用于真实边界：

- 外部 LLM、TTS、RunningHub 和发布平台；
- 数据库、文件系统和对象引用；
- 跨进程、跨服务和操作系统能力；
- 已确认存在多个实现或近期替换点的能力。

普通内部函数、单一稳定实现和局部组件不需要 Interface、Port、Adapter 或依赖注入。容器只负责组装，不能变成隐藏依赖的 Service Locator。

#### 22.11.4 边界校验、权限和异步能力

- 外部输入在 API、文件、Provider 和用户输入边界完成客观结构与安全校验；
- 权限和高风险确认集中在对应资源或领域策略中，不散落在页面和 Router 的条件判断里；
- 长任务、媒体处理、需要恢复、并发控制或外部副作用的操作进入任务执行层；
- 普通同步操作不为了架构统一强制进入队列；
- 事件表达已经发生的事实，并且至少满足一个真实需要：存在多个独立消费者、跨进程边界、需要可靠异步交付，或生产者与消费者生命周期独立；存在必要同步顺序时应直接调用，不能用事件隐藏流程。

#### 22.11.5 成熟能力优先，第三方依赖受控

路由、表单、验证、主题、基础控件、日志、测试、HTTP、存储和常见安全能力，优先使用项目已有且语义匹配的实现、当前技术栈、标准库和成熟框架已经提供的能力。检索和评估深度与变更风险相称，小修改不要求进行框架级选型。

新增第三方依赖前必须确认：

- 当前能力为什么不能满足；
- 项目是否活跃维护；
- 安全记录、许可和供应链风险；
- 包体、运行时和升级成本；
- API 是否稳定；
- 移除或替换是否可控。

“不重复造轮子”不等于为一个简单函数引入大型依赖，也不允许同时引入多个解决同一问题的框架。

#### 22.11.6 测试支持持续设计

测试优先保护用户行为、领域规则、边界和真实纵向闭环。Feature/Integration Test 用于证明用户行为和模块协作；Unit Test 用于证明隔离的领域规则、状态迁移、关键错误路径、纯函数和复杂算法。根据风险选择测试层级，不围绕内部实现细节堆积孤立测试。

重构应在行为测试保护下持续进行，不等待文件变得无法修改后再启动全量重写。

#### 22.11.7 超级文件是评审信号

行数不是自动质量合同，但以下情况必须触发职责检查：

- 一个函数同时完成多个可命名业务步骤；
- 一个 React 组件同时负责 API、领域状态、表单、布局、弹窗和多个副作用；
- 一个 Router、Service、Repository 或页面持续承接不同业务领域；
- 修改一个功能经常需要在同一巨型文件中触碰无关区域；
- 文件已经难以独立理解、测试、评审或删除。

可使用以下软阈值提醒评审，但不得机械按行数拆分：

- 普通函数超过约 80 行；
- React 组件超过约 300–500 行；
- 普通手写源码文件超过约 800–1000 行。

达到提醒阈值后只需在代码评审或变更说明中给出“职责仍单一，保留”或“沿哪些职责拆分”的简短结论，不新增独立审批、合同或门禁。

生成代码、静态数据和第三方文件可以例外。拆分必须沿真实职责、数据所有权和依赖方向进行，不能只把一个巨型文件机械切成多个仍然互相耦合的文件。
