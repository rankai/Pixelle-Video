# Pixelle 项目开发原则

> 状态：项目级强制核心规则。
>
> 用法：所有变更遵守本文件；按风险读取相关 ADR、领域方案和 [`engineering-playbook.md`](engineering-playbook.md) 的对应章节。低风险修改不要求通读工程手册，高风险或架构变更必须检查相关 ADR 和手册章节。

## 1. 目标

Pixelle 要在良好的架构、代码、安全和稳定性底座上敏捷交付功能，并随着真实业务增长从简到繁演进。

默认工程方式是：

> 敏捷纵向交付 + 持续设计 + 模块化单体 + Feature-first + 语义化 Design Token + 只用于真实边界的 Ports/Adapters。

这是一条低决策成本的默认道路，不是要求每个功能建立完整分层、接口、目录、Adapter、队列或合同。架构元素只在当前职责和边界需要时出现。

本原则反对没有现实依据的复杂度，不反对必要的架构、安全、稳定性、可测试性和可维护性投入。

## 2. 十条核心规则

1. 从当前真实问题和根因出发，不从熟悉的技术方案反推需求。
2. 选择职责正确、能够完整解决问题的最低复杂度方案。
3. “最小”不能牺牲单一权威、架构边界、安全、数据一致性和明确失败。
4. 先复用语义匹配的现有能力、标准库和成熟框架，再决定新增实现。
5. 用户可见功能按纵向闭环交付，不合入假成功、无调用者、不可达或只有一半的核心路径。
6. 主观质量由业务流程、模型、Prompt、素材、模板和用户判断解决，不建设伪精确的质量合同。
7. 没有当前事实依据，不增加平台、状态、分支、兼容层、基础设施或未来系统。
8. 临时兼容和发布切换必须单一权威、可观察、可删除，不能层层叠加。
9. 拆函数、组件、文件和功能内模块是职责设计，不要求多个调用方；只有提升为跨功能共享抽象才要求稳定语义和真实复用。
10. 方案、测试、评审、恢复和文档投入与风险相称，小改动不套用重流程，高风险边界不为速度让步。

## 3. 开发前的最小决策

任何变更都要用与风险相称的方式回答：

1. 当前是谁遇到了什么问题，造成了什么影响？
2. 根因是什么，已有实现为什么不能满足？
3. 最小的有效修改是什么，用户或系统行为会怎样变化？
4. 如何用真实结果证明问题被解决？
5. 本次明确不做什么？

风险分级：

- **低风险小改**：简短记录问题、根因、修改和验证；
- **普通功能**：轻量纵向闭环方案，覆盖输入、业务、持久化、UI、失败和测试；
- **高风险变更**：涉及架构边界、安全、权限、持久化、迁移、支付、不可逆外部操作、跨进程协议或新基础设施时，使用完整方案；长期架构决策变化时先修订或新增 ADR。

不得把高风险变更拆小后按低风险处理，也不得用“提高质量”“完善闭环”“增强扩展性”或“为未来准备”代替真实问题。

## 4. 最小充分实现

默认按以下顺序判断，投入深度与变更风险相称：

```text
项目已有且语义匹配的能力
→ 当前技术栈、标准库或已有依赖
→ 修正配置、内容或局部逻辑
→ 扩展现有职责正确的组件或服务
→ 在当前 feature/domain 内新增小模块
→ 多个真实场景稳定后抽取共享能力
→ 有明确触发条件时新增依赖、平台或基础设施
```

复用以语义、行为和所有权匹配为前提。为了复用而不断增加布尔参数、调用方判断和特殊分支，说明抽象边界可能错误。

如果局部修改会继续扩大巨型页面、路由或 Service，复制核心规则，产生多权威、隐藏依赖或循环依赖，应在当前功能内建立职责清楚的小模块。不得为了少新增文件而破坏架构。

## 5. 架构底座与抽象边界

### 5.1 模块化单体和 Feature-first

- 前端按用户功能组织，后端按业务领域和数据所有权组织；
- 页面、Router、脚本和启动入口负责组合，不承载核心业务；
- 一个业务事实只有一个权威所有者；
- 模块内优先直接调用，依赖方向清楚；
- 目录按当前需要创建，不生成空目录、空接口和占位文件。

目录形式是参考，不是门禁。测试可以与源码共置，也可以放在 feature 自己的测试目录；不得只为统一外观迁移现有结构。

### 5.2 职责拆分与共享抽象

以下行为即使只有一个调用方也可以实施：

- 拆分过长函数、前端组件、Hook、样式和功能内 Service；
- 把领域规则从 UI、Router 和脚本入口移入领域模块；
- 把 API、数据转换和持久化访问移入当前功能的 Client、Service 或 Repository；
- 按真实业务步骤、状态所有权和副作用边界拆文件。

这些模块默认留在当前 feature/domain。只有准备建立跨功能公共依赖时，才采用稳定语义、真实调用方和“重复三次”等判断。

同一份权限、计费、状态归属、持久化事实和安全规则从第一次出现起就必须单一权威，不适用“重复三次”。

### 5.3 Ports/Adapters 和依赖装配

Ports/Adapters 只用于真实边界：

- 外部模型、媒体和第三方平台等 Provider；
- 数据库、文件系统、对象存储和操作系统能力；
- 跨进程、跨服务协议；
- 已确认存在多个实现或近期替换点的能力。

普通内部函数、单一稳定实现和局部组件不需要 Interface、Port、Adapter 或依赖注入。依赖在明确的组合入口装配；容器不能成为隐藏依赖的 Service Locator。

### 5.4 Design Token 和公共 UI

品牌色、文字、背景、边框、状态、字体层级、间距、圆角、阴影、焦点、禁用和错误等稳定语义可以从第一次出现进入设计底座。

页面装饰和特殊布局留在 feature 内。两个偶然相同的 CSS 值不构成 Token。基础控件优先使用当前 UI 框架；只有稳定产品语义真实重复时才建立 Pixelle 公共组件。

### 5.5 成熟框架优先

优先复用项目已有且语义匹配的能力，其次使用当前技术栈、标准库和成熟框架已经提供的能力。借鉴成熟框架的约定优于自由发挥、清晰入口、边界验证、依赖装配、迁移和测试实践，但不复制与当前技术栈不匹配的框架模式。

新增第三方依赖前检查当前能力、维护状态、安全与许可、包体与运行成本、API 稳定性和移除成本。一个简单函数不引入大型依赖，同一问题不并存多个框架。

## 6. 合同、异步与自动化

### 6.1 合同只保护客观边界

Schema、合同和状态约束用于外部 API、前后端结构、持久化、权限、租户隔离、支付、幂等、文件媒体引用和稳定跨系统协议。

它们不评价内容是否有感染力、页面是否好看、创意是否高级或用户是否喜欢。结构校验和 repair 只处理字段、类型、枚举和格式等客观错误。

### 6.2 队列、事件和重试

- 普通同步操作不为了架构统一进入队列；
- 长任务、媒体处理、需要恢复、并发控制或外部副作用的操作可以进入任务执行层；
- 事件表达已经发生的事实，并且至少满足一个真实需要：多个独立消费者、跨进程边界、可靠异步交付、生产者与消费者生命周期独立；
- 存在必要同步顺序时直接调用，不能用事件隐藏流程；
- 自动重试只用于可确认的暂时性技术失败，并且操作幂等、次数有限、费用和副作用可控；
- 不因主观结果“不够好”自动评分、重试、降级或生成多套策略。

## 7. 兼容、迁移和低概率分支

向后兼容不是默认要求。旧代码、旧测试、旧 fixture 或草稿合同本身不证明存在兼容需求。

优先在同一受控阶段更新调用方、迁移真实数据并切换唯一权威路径。只有仍存在真实消费者或数据无法安全一次迁移时，才建立临时兼容层，并必须具备：

- 一个权威实现；
- 明确适用范围；
- 可观察的使用情况；
- 删除条件和阶段或日期；
- 旧路径最终删除。

不得叠加兼容层，也不得让临时开关长期保存两套实现。稳定产品能力或权益开关可以长期存在，但必须有业务语义、所有者、默认值、权限边界和启停测试。

低概率、低影响情况默认清楚失败或人工处理；低概率但涉及安全、权限、支付、数据丢失或不可逆操作时，实施必要保护和可靠恢复。不得为极小概率、低损失场景不断增加分支、状态机和恢复平台。

## 8. 完整纵向交付

用户可见功能至少完成当前范围内的：

```text
真实入口 → 输入与权限 → 领域逻辑 → 持久化/外部调用
→ 结果与错误呈现 → 重启或恢复边界 → 测试与真实验收
```

以下不等于功能完成：

- 只有方案、原型、Schema、接口或基础组件；
- 默认关闭且没有真实入口的能力；
- 假成功、模拟结果代替真实执行；
- 无调用者、不可达或只有适配器没有闭环的代码；
- 构建通过但真实用户路径没有运行。

等待第三方授权、付费资源、生产窗口或不可逆人工确认时，可以标记为“实现完成，等待外部验收”，但不能标记为“功能可用”。

## 9. 工程质量底线

最小方案仍必须按当前风险保证：

- **正确性**：领域规则、状态和数据单一权威，错误明确；
- **安全性**：密钥不进入前端、日志或长期证据；外部输入不可信；权限最小化；高风险操作有确认边界；
- **稳定性**：按需处理超时、取消、幂等、并发、事务、资源释放、长任务恢复和外部失败；
- **可维护性**：命名真实，职责单一，不复制核心规则，删除失效代码；
- **扩展性**：通过清晰模块、稳定依赖方向和真实外部边界保留替换点，不提前实现未来功能；
- **可观察性**：关键失败和长任务有足够的非敏感日志、进度与结果；
- **性能**：以测量结果为依据，不凭担忧提前引入缓存或分布式架构。

出现多权威、业务规则复制、循环依赖、Provider 细节进入领域、模块承担多个独立职责、同类修改频繁跨越无关区域，或测试发布排障成本持续上升时，应在当前范围内进行架构调整，不能用“避免过度设计”推迟必要重构。

## 10. 测试与文件职责

测试按风险选择，不按测试类型信仰：

- Feature/Integration Test 证明用户行为、边界协作和纵向闭环；
- Unit Test 证明隔离的领域规则、状态迁移、关键错误路径、纯函数和复杂算法；
- 真实运行或人工验收证明第三方平台、媒体质量和用户操作结果。

测试保护行为，不把内部实现细节、临时结构或主观质量固化成合同。

文件行数只作为职责检查信号，不是自动质量门禁。函数约 80 行、前端组件约 300–500 行、普通手写源码约 800–1000 行时，评审者应说明“职责仍单一，保留”或沿业务职责拆分；不要求单独文档或审批。不得机械切文件，也不得以未达到阈值为由保留明显混杂的职责。

## 11. 完成与评审

完成一项变更必须能回答：

1. 当前真实问题是否被解决？
2. 用户或系统的真实主路径是否运行成功？
3. 是否仍有假成功、不可达代码、重复权威或临时路径？
4. 失败、安全、恢复和数据边界是否与风险相称？
5. 新增复杂度是否少于它消除的复杂度？
6. 是否只修改当前范围，并明确未完成边界？

评审必须同时检查“有没有做多”和“有没有为了少做而牺牲工程质量”。

## 12. 文档优先级

按以下顺序解释决策：

1. 法律、合规、安全、隐私和数据保护的强制约束；
2. 当前明确批准的产品决策决定需求目标和范围；
3. Accepted ADR 在其架构适用范围内保持权威，直到被修订、替代或废弃；
4. 本文件约束实施方式；
5. 领域方案描述当前领域交付，不扩大上位范围；
6. 协调台账控制执行顺序，不把文档、合同和门禁数量当作完成度；
7. 工程手册提供解释和示例，不新增高于本文件的要求。

产品决策改变 Accepted ADR 的架构、安全或数据边界时，必须先同步修订 ADR，不能让冲突规则长期并存。
